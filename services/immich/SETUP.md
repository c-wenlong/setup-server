# immich — self-hosted photo library (Google Photos replacement)

Timeline, albums, sharing, iOS/Android background camera backup, and —
when machine learning is on — semantic search, face grouping and OCR.
Web UI: `https://kai-home-server.taild6a23f.ts.net:2283`.

Chosen over PhotoPrism (no native mobile app, so no background backup;
multi-user is paywalled) and Ente (much lighter server, true E2EE, but
fiddlier MinIO/CORS setup and a smaller community). Immich is the only one
of the three that is a drop-in replacement for what Google Photos actually
does day to day.

## Architecture

Four containers on a Compose bridge network (`name: immich`):

- **immich_server** (`ghcr.io/immich-app/immich-server`) — API + web UI +
  the job workers. The only container with a published port, and it is
  published on `127.0.0.1:2283` only; Tailscale Serve terminates TLS in
  front of it on `:2283`.
- **immich_postgres** (`ghcr.io/immich-app/postgres:14-vectorchord…`) —
  Immich's own Postgres build with the `vectorchord` + `pgvectors`
  extensions. A stock `postgres:16` image **will not work**. No published
  port; reachable only from the other containers.
- **immich_redis** (`valkey`) — job queue. No published port.
- **immich_machine_learning** — CLIP / face / OCR inference. Behind the
  `ml` Compose profile, so it only exists when ML is on. See below.

State lives under `~/services/immich`:

```
~/services/immich/
  library/     # UPLOAD_LOCATION — original photos and videos, thumbnails, transcodes
  postgres/    # DB_DATA_LOCATION — must be local disk, never a network share
  .ml-mode     # "on" | "off" — the last ML mode setup.sh deployed
```

Model weights live in the `model-cache` Docker volume (only when ML is on).

## Machine learning (the RAM decision)

Immich documents **6 GB RAM minimum, 8 GB recommended**, and the ML
container is most of that. This box has 7.7 GB total and ollama alone
claims ~5 GB while a model is loaded — so **ML is off by default**:

```bash
./setup.sh                # ML off (default)
IMMICH_ML=on  ./setup.sh  # turn it on
IMMICH_ML=off ./setup.sh  # turn it back off
```

| | ML off | ML on |
|---|---|---|
| Upload, timeline, albums, sharing | ✅ | ✅ |
| Phone background backup | ✅ | ✅ |
| Search by date / place / filename | ✅ | ✅ |
| Semantic ("smart") search | ❌ | ✅ |
| Face detection + people grouping | ❌ | ✅ |
| OCR / text in images | ❌ | ✅ |
| Extra RAM | — | ~2–3 GB (capped at `ML_MEM_LIMIT`, default 3g) |

Flipping the flag is a complete operation: setup.sh starts or removes the
container, flips `machineLearning.enabled` through the admin API, and
records the new mode in `.ml-mode`. Turning ML on later backfills existing
photos — the Smart Search and Face Detection jobs just run over the library
(slowly, at concurrency 1). Nothing needs re-uploading.

Do not "enable ML" by editing the setting in the web UI alone: with the
container absent the jobs queue up and fail. Use the flag.

## Security model

- Tailnet-only. The server binds `127.0.0.1`; Postgres and Redis publish no
  ports at all. Nothing is reachable from the LAN or the internet.
- Immich has its own login (unlike code-server, its API is stateful and the
  mobile apps need credentials), so the tailnet is the outer boundary and
  the admin account is the inner one.
- Credentials are generated by setup.sh into the gitignored `.env`
  (mode 600): `DB_PASSWORD` and `IMMICH_ADMIN_PASSWORD`.
- The admin account is created via `POST /api/auth/admin-sign-up` on first
  deploy — there is no window where an unauthenticated stranger on the
  tailnet can claim the admin slot by loading the page first.

⚠️ Same password-sync rule as every other service here: if you change the
admin password in the web UI, mirror it into `.env`. setup.sh logs in with
the `.env` copy to manage settings; on a mismatch it warns and skips the
settings step rather than failing the deploy.

## Dependencies

| Needs | Why | Checked by preflight |
|---|---|---|
| Linux or macOS | systemd/launchd not used — Docker restart policy handles boot | ✅ |
| Docker + Compose v2 | all four containers | ✅ (incl. daemon reachability) |
| curl | health checks + the Immich REST API | ✅ |
| python3 | JSON for the admin/settings API calls | ✅ |
| Tailscale, logged in | publishing | ✅ (BackendState must be `Running`) |
| x86-64-v2 CPU | the v3 ML image requires it | ✅ (only when ML is on) |
| ≥ 20 GB free disk | media library | ⚠️ warns |
| ≥ 8 GB RAM with ML on | documented recommendation | ⚠️ warns |

## Deploy

```bash
cd services/immich && ./setup.sh     # idempotent; rerun to upgrade/repair
```

Step by step:

1. **Preflight** — OS, non-root, curl, python3, Docker daemon, Compose v2,
   Tailscale running, numeric ports, valid `IMMICH_ML`, and (ML on only)
   the x86-64-v2 CPU feature check. Then RAM and free-disk advisories.
2. **`.env`** — written only if absent, mode 600: generated hex `DB_PASSWORD`
   (Immich requires `[A-Za-z0-9]` only) and `IMMICH_ADMIN_PASSWORD`, paths
   under `~/services/immich`, `IMMICH_VERSION=v3`, and `TZ` read from
   `readlink /etc/localtime`. `COMPOSE_PROFILES` is the one line setup.sh
   owns and will rewrite — only when you pass `IMMICH_ML` explicitly.
3. **Compose up** — with `--profile ml` when ML is on. First run pulls ~2 GB.
   If ML just went off, the stale container is removed.
4. **Wait for `/api/server/ping`** — up to 4.5 minutes; first boot runs the
   DB migrations, which are slow on spinning disks.
5. **Admin account** — `POST /api/auth/admin-sign-up`. HTTP 400 means an
   admin already exists, which is the normal re-run path and is not an error.
6. **Settings** — `GET` the admin config, patch only the keys we own, `PUT`
   it back. The endpoint moved from `/api/system-config` to
   `/api/admin/config` after v3.1.0, so setup.sh probes for the new path and
   falls back — v3.1.0 (deployed today) uses the old one. The **first**
   settings pass applies the low-RAM tuning (see below); later runs touch the
   ML toggle and nothing else, so anything you changed in the web UI survives
   a re-run. Skipped entirely if login fails.

   "First" here means the `.ml-mode` marker is absent, not "the admin was
   just created" — so if a run dies between creating the admin and writing
   settings, the next run still applies the tuning instead of skipping it.
7. **`tailscale serve --bg --https=2283`**, with the operator-grant and
   approval-link fallbacks.
8. **Verify** end to end over HTTPS, then print the URL, credentials, phone
   setup and the Takeout import command.

### Low-RAM tuning applied on first deploy

Straight from the Immich FAQ's advice for an overloaded host:

| Setting | Value | Default |
|---|---|---|
| `job.smartSearch.concurrency` | 1 | 2 |
| `job.faceDetection.concurrency` | 1 | 2 |
| `job.thumbnailGeneration.concurrency` | 1 | 3 |
| `job.videoConversion.concurrency` | 1 | 1 |
| `job.ocr.concurrency` | 1 | 2 |
| `ffmpeg.threads` | 2 | 0 (all cores) |
| `machineLearning.facialRecognition.modelName` | `buffalo_s` | `buffalo_l` |

These are first-run defaults, not policy: change them in Administration →
Settings whenever the box gets more headroom, and re-running setup.sh will
not undo it.

## Client side

**Phone (the whole point).** Install Immich from the App Store / Play Store,
tap **Server Endpoint**, enter `https://kai-home-server.taild6a23f.ts.net:2283/api`,
log in with the `.env` credentials, then enable background backup. The phone
must be on the tailnet (Tailscale app connected) for backup to run — off the
tailnet it queues and uploads next time it connects.

⚠️ **Turn off Seafile camera upload before enabling Immich's.** Running both
stores every photo twice on a box with ~150 GB free. Seafile stays the Drive;
Immich becomes the photo system.

**Importing Google Takeout.** Use `immich-go`, not the web uploader — it
reads the Takeout JSON sidecars, so albums, original dates and geodata
survive:

```bash
immich-go upload from-google-photos \
  --server=https://kai-home-server.taild6a23f.ts.net:2283 \
  --api-key=<Account Settings → API Keys> \
  takeout-*.zip
```

Run it overnight, and expect the job queue to stay busy long after the
upload finishes. A long queue is not a broken server.

## Ops

- Status: `docker compose --project-directory . ps`
- Logs: `docker compose --project-directory . logs -f immich-server`
- Upgrade: `docker compose --project-directory . pull && ./setup.sh`
  (setup.sh re-applies serve config and re-verifies; it will not touch your
  settings)
- Stop / start: `docker compose --project-directory . down` / `up -d`
  — note that a bare `up -d` respects `COMPOSE_PROFILES` in `.env`, so it
  starts the ML container iff ML is on.
- Remove: `./teardown.sh` (or Remove in the launcher) unpublishes every Serve
  port pointing at `:LOCAL_PORT`, stops the server and ML container before
  Redis and Postgres, then `down`. Photos, database, the model-cache volume and
  `.env` stay, so `./setup.sh` brings it back. `./teardown.sh --purge` also
  deletes the library, the database, the model-cache volume (`down -v`),
  `.ml-mode` and `.env`, after you type `immich`. Nothing backs the photos up:
  copy them out first. It refuses a library outside `~/services/immich`.
- Back up: `~/services/immich/library` (the photos) plus a database dump.
  Copying `~/services/immich/postgres` while Postgres is running is not a
  valid backup — use Immich's own database backups (Administration →
  Settings → Backup) or `pg_dumpall` against the container.

## Tests

```bash
./tests/run-tests.sh          # mocked, safe anywhere
./tests/run-tests.sh --live   # verify this machine's real deployment
```

The mocked suite runs the real `setup.sh` against a sandboxed `$HOME` with
PATH stubs. The `curl` stub fakes the Immich REST API — including
"admin already exists" and "password changed in the UI" — so the admin
bootstrap and the settings PUT are genuinely exercised, with real `python3`
doing the JSON on both sides. Covered: preflight failures (docker perms,
Tailscale down, bad port, bad `IMMICH_ML`), fresh deploy with ML off and on,
idempotent re-run, the ML on→off flip, password drift, operator escalation,
and the serve-approval prompt.

## Notes

- Port 2283 is Immich's default and the HTTPS port matches the local port,
  following the newer convention in this repo.
- The compose file pins the redis and postgres image digests exactly as
  upstream ships them, and pins the app to the `v3` tag rather than
  `release`, so a `docker compose pull` cannot jump a major version by
  surprise. Bump `IMMICH_VERSION` in `.env` deliberately, and read the
  release notes first — Immich's breaking changes are real.
- Postgres `shm_size` is raised to 1 GB (upstream default 128 MB): HNSW
  index builds on the vector columns otherwise fail with "could not resize
  shared memory segment" partway through a large import.
- Do not point `UPLOAD_LOCATION` at a network share; Immich supports it for
  media but never for the database, and mixed setups are a common source of
  corruption reports.
