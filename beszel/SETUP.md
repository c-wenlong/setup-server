# beszel — resource monitoring

CPU, RAM, GPU (NVIDIA), disk usage + I/O, network, and temperature graphs
with history and threshold alerts, complementing Uptime Kuma (which only
answers "is it up?"). Dashboard: `https://kai-home-server.taild6a23f.ts.net:8092`.

## Architecture

Two parts:

- **Hub** (`henrygd/beszel` Docker image): PocketBase-backed web UI + store.
  Host networking, bound to `127.0.0.1:8092` (`serve --http` override in
  docker-compose.yml), published tailnet-only via `tailscale serve :8092`.
  Data in `~/services/beszel/hub`.
- **Agent** (native Go binary, `~/.local/bin/beszel-agent`, systemd **user**
  unit `beszel-agent.service`): reads /proc, hwmon temps, `nvidia-smi` (GPU
  stats — needs no container toolkit precisely because it is NOT in Docker),
  and the docker socket for per-container stats. Listens `127.0.0.1:45876`;
  the hub connects to it over SSH protocol using a hub-generated keypair.

Host networking on the hub is load-bearing: on the bridge network the hub's
`127.0.0.1` is its own namespace and it can never reach the agent.

## Security model

- Tailnet-only: hub on loopback + Tailscale Serve; agent on loopback.
- Admin credentials generated by setup.sh into the gitignored `.env`
  (mode 600). The UI user and the PocketBase superuser share them.
- The agent's `KEY` (hub public key) is not secret; it only lets the hub
  *authenticate itself to* the agent.

## Deploy

```bash
cd beszel && ./setup.sh     # idempotent; rerun to upgrade/repair
```

setup.sh does everything via the hub's API — superuser, UI user, agent key
fetch, agent install + unit, system registration, tailscale serve — and
fails loudly if the agent doesn't report within 60s. No manual UI steps.

## Ops

- Status: `systemctl --user status beszel-agent`, `docker logs beszel`
- Upgrade: `docker compose --project-directory . pull && ./setup.sh`;
  agent: delete `~/.local/bin/beszel-agent`, rerun setup.sh
- Alerts: configure per-metric thresholds in the UI (user icon → Notifications
  → add ntfy URL `http://127.0.0.1:3003/alerts`) — RAM% is the one that
  matters most on this 7.7 GB box.
- Kuma probes `http://127.0.0.1:8092/api/health` (seeded via
  `monitoring/seed_kuma.py`).

## Testing note

`tests/run-tests.sh` runs static structural checks in mocked mode (this
service's setup leans on the hub's live API, so the full PATH-stub sandbox
used by older services would mostly test the stubs); `--live` verifies the
real deployment end to end, including that stats are fresh.
