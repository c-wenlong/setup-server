# Features
One-shot, idempotent deploy scripts that install and verify self-hosted services on a home server, with tailnet-only publication via Tailscale Serve for published services, plus a launcher web app to run them.

## Deploy and upgrade
- **Deploy a service**: run one service's `setup.sh` as a regular user to install it, configure it, make it boot-persistent, verify it, and print management commands; published services also get tailnet-only HTTPS, end-to-end verification and a URL, while Ollama stays loopback-only and deployd and ntfy-control are headless jobs. Status: stable. Surface: CLI. Entry point: `cd services/<service> && ./setup.sh`. Tests: `services/*/tests/run-tests.sh`.
- **Upgrade or repair in place**: re-run the same `setup.sh` to upgrade or repair a deployment without overwriting a config file you edited and without sudo on later runs. Status: stable. Surface: CLI. Entry point: `cd services/<service> && ./setup.sh` (re-run). Tests: `services/*/tests/run-tests.sh`.
- **macOS deploys**: run supported services' `setup.sh` on macOS, where native services become launchd LaunchAgents and Docker services run under Docker Desktop or OrbStack; Remote desktop is Linux-only. Darwin branches have mocked checks only (portable by construction, not yet verified on a real Mac per README.md and DIRECTORY.md). Status: beta. Surface: macOS. Entry point: `services/<service>/setup.sh`. Tests: `services/*/tests/run-tests.sh`.
- **Install from the launcher**: press Install on a not-installed service to run its `setup.sh` as a job with a streamed log and an install receipt. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/catalogue (or Install on a home-page row; API `POST /api/services/<key>/deploy`). Tests: `app/web/tests/test_server.py`.
- **One-tap image updates**: see which services' image tags moved upstream (background registry digest check every 6 hours, or a check-now button) and press Update to pull and re-run `setup.sh`. Status: stable. Surface: web. Entry point: Update on https://kai-home-server.taild6a23f.ts.net:8093/#/service/<key> (API `POST /api/services/<key>/update`, `POST /api/services/<key>/updates/check`). Tests: `app/web/tests/test_server.py`.

## Remove
- **Remove a service, keep its data**: run `teardown.sh` with no flags to unpublish every Serve port that proxies only to that service and stop it, leaving the data dir and `.env` so `./setup.sh` restores it. Status: stable. Surface: CLI. Entry point: `cd services/<service> && ./teardown.sh` (all 37 services ship one; design in `docs/teardown-sh.md`). Tests: `services/*/tests/run-tests.sh`.
- **Purge a service's data**: run `teardown.sh --purge`, type the service name back to confirm, and it also deletes the service's data dir and `.env` under `~/services/<service>`; Kopifund preserves its data folder (`~/.kopifund`), and Hermes Studio preserves its catalog/data root (`HERMES_HOME`, formerly `GNOSIA_HOME` or `SELF_LEARN_HOME`); a wrong confirmation changes nothing. Status: stable. Surface: CLI. Entry point: `./teardown.sh --purge` (terminal only; the launcher never sends it). Tests: `services/*/tests/run-tests.sh`.
- **Remove from the launcher**: press the red Remove button on a service's page (or a catalogue card) to pause its Uptime Kuma monitor and run its `teardown.sh` with no flags, so data and `.env` stay. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/service/<key> (API `POST /api/services/<key>/action` with `{"action": "remove"}`). Tests: `app/web/tests/test_server.py`.
- **DNS stop guard**: AdGuard's Stop and Remove are refused while it may still be the tailnet's DNS server, with the reason shown, via a read-only check. Status: stable. Surface: CLI. Entry point: `services/adguard/teardown.sh --check-dns` (named as `control.stop_guard` in `services/adguard/app.json`). Tests: `services/adguard/tests/run-tests.sh`.

## Service control
- **Start, stop and restart from the launcher**: start, stop or restart any controllable service from its row or ⌘K menu; Stop pauses its Uptime Kuma monitor and Start resumes it, and the launcher and ntfy themselves are locked against Stop. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/ (API `POST /api/services/<key>/action`; allowlist is the `control` block in `app/web/services.json`). Tests: `app/web/tests/test_server.py`.
- **ntfy-control: control services from the phone**: send commands (or tap the `panel` menu card) on the ntfy topic `control` to start, stop or restart allowlisted services and launcher apps, with replies and Kuma monitor pausing. Status: stable. Surface: job. Entry point: `services/ntfy-control/setup.sh` (systemd user unit running `services/ntfy-control/control_listener.py`; no HTTP port of its own). Tests: `services/ntfy-control/tests/run-tests.sh`.

## Auto-redeploy (deployd)
- **deployd: push-to-deploy without inbound webhooks**: a poller pulls this checkout fast-forward, watches each `deploy` block (`repo`/`ref`/`cmd`) in `services/*/app.json` plus custom pollers, and runs the deploy command when the watched ref moves, backing off 15 minutes per failed commit. Status: stable. Surface: job. Entry point: `services/deployd/setup.sh` (systemd user timer, default every 60 s; state in `~/services/deployd/state/`). Tests: `services/deployd/tests/run-tests.sh`.
- **Deploys page**: see deployd's state (Polling, Paused, Timer failed) and every watched repo, pause, resume or restart the timer, and add, pause, restore, force-deploy or remove pollers. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/deploys (API `GET /api/deployd`, `/api/deployd/pollers/<key>`). Tests: `app/web/tests/test_server.py`.
- **Edit poll cadence**: see the poll cadence and last-poll timing in the Deploys header and edit `POLL_SECONDS`, which re-runs deployd's `setup.sh` (unreleased in CHANGELOG.md). Status: beta. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/deploys. Tests: `app/web/tests/test_server.py`.
- **Deployments gallery**: browse every app and deployd-watched service as cards with state, method, deployed commit and age, open one to edit how it deploys, and redeploy it (added 2026-11-04, SPEC v15–v16). Status: beta. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/deploys/<key> (API `GET /api/deployments`, `PUT /api/deployments/<key>`, `POST /api/deployments/<key>/redeploy`). Tests: `app/web/tests/test_server.py`.
- **Commits-behind check**: press Refresh on a deployment page to see how many commits the deployed sha trails its watched ref by, with the list of missing commits (unreleased in CHANGELOG.md). Status: beta. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8093/#/deploys/<key> (API `POST /api/deployments/<key>/check`). Tests: `app/web/tests/test_server.py`.

- **New app from a GitHub repo**: pick a repo (private ones through the box's `gh` login) and deploy it as an app on its own port in 8300–8399 from a Dockerfile or as a static site, with a health check and automatic rollback to the previous image when the new one is unhealthy (added 2026-10-28, static method and proxy rules 2026-11-05). Status: beta. Surface: web. Entry point: + New app on https://kai-home-server.taild6a23f.ts.net:8093/#/deploys (API `POST /api/apps`; runner `app/web/ghapp.py deploy|remove <key>`). Tests: `app/web/tests/test_ghapp.py`, `app/web/tests/test_server.py`.
- **Export and restore app definitions**: export an app's definition to this repo as a pull request (variable names only, never values), and reinstall any exported app on a box that lacks it (added 2026-10-28). Status: beta. Surface: web. Entry point: Source section on an app's page (API `POST /api/apps/<key>/export`; definitions in `app/web/apps/`). Tests: `app/web/tests/test_server.py`.

## Health checks and monitoring
- **Uptime Kuma: seeded uptime monitors**: see every published service's health on a dashboard that `setup.sh` seeds with one monitor per entry in `PUBLISHED`, each on a health path chosen to fail when the service is broken, plus loopback monitors for ollama and the hermes-agent API. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:3002/ (redirects to `/dashboard`; Kuma does not monitor itself; seeding in `services/monitoring/seed_kuma.py`, deployed by `services/monitoring/setup.sh`). Tests: `services/monitoring/tests/run-tests.sh`.
- **ntfy: phone alerts**: get push notifications on the phone or web from Kuma alerts on the `alerts` topic. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:3003/ (health `/v1/health`; deployed by `services/monitoring/setup.sh`). Tests: `services/monitoring/tests/run-tests.sh`.
- **Beszel: resource monitoring**: see CPU, RAM, GPU, disk, network and temperature graphs with history and alerts, from a Docker hub plus a native agent on loopback; its default suite checks setup and Compose statically and runs teardown in a sandbox with stubs generated at runtime. Status: stable. Surface: web. Entry point: https://kai-home-server.taild6a23f.ts.net:8092/ (health `/api/health`; `services/beszel/setup.sh`). Tests: `services/beszel/tests/run-tests.sh`.
- **Live verification suites**: run a service's `--live` suite on the box to check its unit or containers, lingering, local health endpoint, that nothing listens off loopback (or off the tailnet IP for the sanctioned exceptions), its Serve mapping, and HTTPS end to end. Status: stable. Surface: CLI. Entry point: `services/<service>/tests/run-tests.sh --live`, or `make test-live` for all. Tests: `services/*/tests/run-tests.sh`.

## Repo checks and CI
- **Mocked suites for every service**: run service suites with a pass/fail summary and no host changes, normally in a sandbox (temp `$HOME`, PATH stubs); Beszel instead checks setup and Compose statically and runs teardown in a sandbox with stubs generated at runtime. Status: stable. Surface: CLI. Entry point: `make test` (one service: `./tests/run-tests.sh` in its folder). Tests: `services/*/tests/run-tests.sh`, `app/web/tests/run-tests.sh`.
- **Per-service contract check**: check that every service has `setup.sh`, `SETUP.md`, `TROUBLESHOOT.md`, tests and stubs, sources `lib/common.sh`, and has rows in README.md and DIRECTORY.md; Beszel is exempt from a checked-in `tests/stubs/` directory, and its `setup.sh` is exempt from sourcing `lib/common.sh`. Status: stable. Surface: CLI. Entry point: `make structure` (`scripts/check-structure.sh`). Tests: `scripts/tests/test-check-structure.sh`.
- **Lint and registry drift check**: run shellcheck over every shell file and stub, the structure check, the check that `app/web/services.json` matches every `app.json`, and actionlint. Status: stable. Surface: CLI. Entry point: `make lint` (`make registry` runs `scripts/build-registry.py --check`). Tests: `scripts/tests/test-build-registry.sh`.
- **Shared helper and tooling suites**: run the suites for `lib/common.sh` and the repo's migration scripts. Status: stable. Surface: CLI. Entry point: `make test-scripts`. Tests: `scripts/tests/test-*.sh`.
- **Launcher Python tests with coverage**: run the launcher and GitHub-app runner unit tests under coverage. Status: stable. Surface: CLI. Entry point: `make test-python`. Tests: `app/web/tests/test_server.py`, `app/web/tests/test_ghapp.py`.
- **CI on pull requests**: every PR and push to `main` runs lint, the per-service mocked suites as a matrix, the Python tests with coverage, a Python syntax compile on the oldest and newest supported versions, and a gitleaks secret scan. Status: stable. Surface: job. Entry point: `.github/workflows/ci.yml`. Tests: none.
- **Pre-commit hooks**: run shellcheck, gitleaks, the structure check and basic file hygiene on every commit. Status: stable. Surface: CLI. Entry point: `pre-commit install` (`.pre-commit-config.yaml`). Tests: none.
